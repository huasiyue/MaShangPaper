# MaShangPaper Markdown 论文转 Word 技术方案

## 1. 文档目标

本文档用于明确 `MaShangPaper` 的推荐实现路线。项目目标是：

- 在不依赖 Pandoc 的前提下，基于 Python 与 OOXML/`python-docx` 实现 Markdown 到 Word 的论文生成能力。
- 支持高校论文场景中的重点格式要求，例如中英文字体混排、标题层级、摘要、参考文献、图表题注、三线表、页眉页脚与页码。
- 为不同学校提供可扩展的格式配置与审查机制，而不是把规则散落在业务代码中。

本文档以 `docs/data` 下的参考脚本为事实基础，重点是把现有思路整理为一条更清晰、可落地的实施路径。

## 1.1 明确技术栈

根据当前约束，推荐技术栈固定为：

- 前端：Vue 3
- UI 组件库：Arco Design Vue
- 后端：Python FastAPI
- Word 生成与格式控制：`python-docx` + 必要的 OOXML 底层注入

这意味着本文档后续提到的页面组织、接口设计、状态管理和组件选型，都以 `Vue 3 + Arco Design Vue + Python FastAPI` 为前提，而不再采用泛前端或其他 UI 框架表述。

## 2. 当前参考实现概览

仓库中已经存在两份很有价值的参考脚本，它们分别对应两类能力。

### 2.1 Markdown 转 Word 生成器

文件：`docs/data/convert_to_word.py`

该脚本已经验证了以下能力：

- 读取 Markdown 文件并输出 `.docx`。
- 设置页面边距、装订线与基础样式。
- 识别多级标题并映射到 Word `Heading` 样式。
- 处理摘要、参考文献、列表、引用块、代码块。
- 处理图表题注、图片占位、表格与三线表边框。
- 对正文、标题、参考文献中的中英文混排字体进行区分设置。

这说明项目的“生成阶段”已经有比较完整的原型基础，不需要从零开始设计。

### 2.2 论文格式化与审查器

文件：`docs/data/yzu_thesis_formatter.py`

该脚本已经验证了以下能力：

- 读取现有 Word 文档并重新套用扬州大学论文规范。
- 支持“毕业论文”与“毕业设计报告”两种格式差异。
- 统一页面设置、页眉页脚、页码、标题、摘要、正文、署名、题注等样式。
- 审查摘要、参考文献、署名等关键结构。
- 输出格式审查报告，便于人工复核。

这说明项目的“格式修正与审查阶段”已经具备原型基础。

### 2.3 结论

结合两份参考实现，当前最合理的技术路线不是重新写一套全新的单体脚本，而是抽象为一个“两阶段流水线”：

1. Markdown 解析并生成结构化初稿 Word。
2. 按学校规范进行二次格式化与审查。

这样可以最大化复用已有能力，也更适合后续扩展多学校模板。

## 3. 推荐总体方案

### 3.1 核心原则

- 纯 Python 方案：核心依赖 `python-docx`，避免额外安装 Pandoc 等外部工具。
- 配置驱动：学校差异尽量收敛到配置层，而不是堆叠在条件分支中。
- 两阶段处理：先生成，再格式化与审查，便于问题定位和能力复用。
- OOXML 精准介入：只有在 `python-docx` 不足以表达需求时，才直接修改底层 XML。
- 可回放与可审查：输出文档的同时，尽量保留日志、规则命中信息与审查报告。

### 3.2 推荐处理流程

```text
Markdown 输入
  -> 语法预处理
  -> 结构识别（标题、摘要、关键词、图、表、参考文献）
  -> 初稿 DOCX 生成
  -> 学校格式器应用
  -> 格式审查报告生成
  -> 下载 DOCX / 查看审查结果
```

### 3.3 为什么建议分成两阶段

直接把“Markdown 解析”和“学校格式规则”揉在一个函数里，短期看起来快，长期会很难维护。分层后的收益更明显：

- Markdown 层只关心“文档结构是什么”。
- 学校格式层只关心“这些结构应该长成什么样”。
- 同一份 Markdown 解析结果，可以复用到不同学校模板。
- 同一套学校规则，也可以应用到外部导入的 Word 文档。

## 5. 模块职责设计

### 5.1 `markdown_parser`

职责：

- 解析 Markdown 文本。
- 识别文档结构块，例如标题、正文、列表、引用、代码块、图、表、参考文献。
- 输出统一的中间结构，例如 `DocumentModel` / `Block[]`。

建议：

- 不要在解析器里直接写学校格式规则。
- 先限定一个“论文 Markdown 子集”，降低歧义。
- 对摘要、关键词、参考文献单独建结构类型，避免后续靠正则反复猜测。

### 5.2 `docx_generator`

职责：

- 把结构化中间模型转换成初稿 `.docx`。
- 负责标题样式映射、正文段落、图表占位、基础页面设置。
- 复用 `convert_to_word.py` 中已经验证过的逻辑。

适合保留在生成阶段的能力：

- 页面边距与基础样式初始化。
- `Heading 1/2/3` 等标准样式设置。
- 图片占位与图表题注生成。
- 表格写入与三线表边框注入。
- 参考文献段落生成。

### 5.3 `formatters/base.py`

职责：

- 定义统一格式器接口。
- 抽象页面设置、标题格式、摘要格式、正文格式、参考文献格式、页眉页脚、审查规则等通用方法。

建议接口示意：

```python
class BaseFormatter:
    def apply_page_setup(self, doc): ...
    def apply_header_footer(self, doc): ...
    def format_paragraph(self, paragraph, context): ...
    def format_table(self, table, context): ...
    def review(self, doc) -> ReviewReport: ...
```

### 5.4 `formatters/yzu.py`

职责：

- 承接 `yzu_thesis_formatter.py` 中已验证的扬州大学规则。
- 支持 `thesis` 与 `design_report` 两种模式。
- 提供格式应用和审查报告能力。

建议抽象出的配置项包括：

- 页面边距、装订线、页眉页脚距离。
- 中文字体、英文字体、摘要字体、署名字体。
- 各级标题字号与对齐方式。
- 摘要长度、参考文献格式、题注格式等校验规则。

### 5.5 `review_report`

职责：

- 将规则命中结果输出为结构化报告。
- 可先支持文本报告，后续再扩展为 JSON 返回给前端。

建议输出内容：

- 错误、警告、提示三级问题。
- 问题位置、当前值、期望值、修正建议。
- 总数统计与格式规范摘要。

## 6. 学校格式扩展策略

### 6.1 优先使用配置，而不是复制逻辑

如果后续要支持更多学校，优先新增配置文件，不要复制一份新的格式化脚本。适合抽成配置的数据包括：

- 页面参数。
- 字体与字号。
- 一级标题是否居中。
- 摘要字体与长度要求。
- 页眉文案。
- 参考文献格式要求。

### 6.2 何时需要自定义格式器

当学校要求出现以下情况时，再考虑新增专属格式器：

- 标题编号体系完全不同。
- 目录、封面、声明页有独特结构。
- 图表编号规则不同。
- 需要注入额外的 OOXML 节点。

### 6.3 建议优先级

第一阶段先把“扬州大学”打磨成稳定模板，再考虑复制到其他学校。单校跑通比多校半成品更有价值。

## 7. 前后端协作建议

### 7.1 后端接口建议

可优先设计以下接口：

- `POST /api/documents/convert`
  - 输入：`content`、`school_id`、`thesis_type`
  - 输出：生成后的 `.docx`
- `POST /api/documents/review`
  - 输入：上传的 `.docx`、`school_id`、`thesis_type`
  - 输出：审查报告
- `POST /api/documents/format`
  - 输入：上传的 `.docx`、`school_id`、`thesis_type`
  - 输出：格式化后的 `.docx` 与审查结果

后端实现建议：

- 使用 FastAPI 的 `UploadFile` 处理 Word 文件上传。
- 使用 `Form` 处理 `content`、`school_id`、`thesis_type` 等表单字段。
- 文件导出统一返回 `FileResponse` 或流式响应。
- 审查结果优先返回 JSON，便于前端用表格和提示组件展示。

### 7.2 前端职责建议

前端采用 Vue 3 + Arco Design Vue，重点放在：

- Markdown 编辑。
- 学校与文档类型选择。
- 转换进度提示。
- 下载生成后的文档。
- 展示格式审查报告。

不建议把格式规则判断放到前端，前端只做输入与结果展示。

推荐的页面拆分方式：

- `EditorPage`：主页面，负责论文内容编辑与导出。
- `SchoolSelector`：学校与论文类型选择。
- `ExportPanel`：转换、格式化、下载操作区。
- `ReviewResultTable`：展示错误、警告、提示三级审查结果。

推荐优先使用的 Arco 组件：

- 表单区：`a-form`、`a-select`、`a-radio-group`、`a-upload`
- 操作区：`a-button`、`a-space`、`a-card`、`a-spin`
- 结果区：`a-table`、`a-tabs`、`a-tag`、`a-alert`、`a-message`

如果需要 Markdown 编辑器，可采用“外部 Markdown 编辑组件 + Arco 外层布局”的组合模式，不建议自行从零实现编辑器。

## 8. 分阶段实施计划

### 阶段一：整理现有参考脚本

目标：

- 提取 `convert_to_word.py` 的通用生成逻辑。
- 提取 `yzu_thesis_formatter.py` 的格式配置与审查逻辑。
- 消除重复代码与脚本式入口依赖。

产出：

- 可复用的 Python 模块。
- 最小可运行的本地转换流程。

### 阶段二：建立统一中间模型

目标：

- 将 Markdown 解析结果转为结构化对象。
- 降低后续新增学校时的改动范围。

产出：

- `DocumentModel`
- 标题、正文、图表、参考文献等块级结构定义

### 阶段三：接入 Web 服务

目标：

- 提供 FastAPI 接口。
- 支持上传、转换、格式化与报告下载。

产出：

- 后端 API。
- 临时文件管理机制。
- 错误处理与日志记录。

### 阶段四：接入前端编辑器

目标：

- 基于 Vue 3 与 Arco Design Vue 完成在线 Markdown 编辑与一键导出。
- 在前端展示格式审查结果。

产出：

- Arco 风格的编辑器页面。
- 学校模板切换。
- 下载与审查报告视图。

### 阶段五：增强能力

后续可逐步加入：

- 图片真实插入，而不是占位。
- 参考文献自动编号与规范化。
- 模板封面生成。
- 临时文件定时清理。
- 多学校配置管理。

## 9. 风险与处理建议

### 9.1 Markdown 语法自由度过高

风险：

- 用户输入风格不统一，会导致标题、摘要、题注识别不稳定。

建议：

- 明确支持的 Markdown 子集。
- 提供示例模板。
- 对高风险结构增加显式标记约定。

### 9.2 `python-docx` 能力边界

风险：

- 某些 Word 细节无法直接通过高级 API 控制。

建议：

- 保留 OOXML 直接注入能力。
- 将 XML 操作封装成独立函数，避免散落在业务流程中。

### 9.3 多学校需求膨胀

风险：

- 如果一开始就追求“支持所有学校”，代码会很快失控。

建议：

- 先完成单校闭环。
- 通过配置抽象沉淀可复用能力，再扩展第二所学校。

### 9.4 生成文档仍需人工复核

风险：

- 高校格式要求细碎，自动化很难一次覆盖全部边缘情况。

建议：

- 默认输出审查报告。
- 把“自动生成 + 人工复核”作为稳定流程，而不是承诺完全无人工介入。

## 10. 验收标准

第一版建议以以下标准验收：

- 能将规范 Markdown 成功转换为 `.docx`。
- 能正确处理标题、正文、摘要、参考文献、图表题注与表格。
- 能应用扬州大学论文格式，并区分毕业论文与毕业设计报告。
- 能生成可读的格式审查报告。
- 代码结构清晰，学校规则位于配置或格式器层，而不是散落在接口层。

## 11. 当前最值得优先落地的事项

如果按投入产出比排序，建议优先做下面三件事：

1. 把两份参考脚本拆成模块，建立统一调用入口。
2. 先打通“Markdown -> 初稿 DOCX -> 扬州大学格式化 -> 审查报告”的闭环。
3. 在闭环稳定后，再接前端编辑器与多学校扩展。

这条路线比直接开始写前端页面、或者一开始就追求多学校支持，更稳、更容易验证成果。
